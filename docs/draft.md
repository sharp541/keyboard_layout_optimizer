# AZIK 系拡張最適化の仕様草案

## 背景

現状の最適化対象は「物理キー位置に対して、1 文字を 1 キーへ割り当てる論理配列」である。
評価関数も `LogicalLayout` 上の文字列 3-gram をそのまま `PhysicalLayout` の打鍵コストへ変換している。

この現行評価は今後も英語ソースに対しては維持し、日本語ソースに対してのみ AZIK 系拡張評価を適用する。
最終的には、英語評価と日本語評価を別々に計算したうえで重み付き合成する。

一方で AZIK 系の入力では、打鍵列と出力列は 1:1 ではない。

- 子音 + 子音で二重母音を出す
- 子音 + 子音で撥音 `ん` を出す

今回やりたいことは、個別の短縮規則を先に固定することではなく、
「どの物理位置に母音・子音・拡張用キーを置くか」を最適化し、その配置から自然に短縮入力が決まるようにすることだと理解している。

## ユーザー前提の妥当性

### 1. 規則探索は「配置から誘導される」という考え方

この方向は部分的に妥当で、初期設計として有力である。

妥当な点:

- AZIK 系短縮は、個々の文字規則よりも「子音列のパターン」で定義しやすい
- 個別規則を大量に持つより、子音/母音/機能キーの役割を配置に持たせたほうが探索対象を整理しやすい
- `子音キー + 機能キー` の組を高頻度モーラへ対応づけると、配置最適化と規則最適化を同時に扱いやすい

ただし、そのままでは不十分な点もある。

- 物理配列だけでは「その 2 打が何へ展開されるか」は決まらない
- 少なくとも「キーの役割」と「2 打列をどう解釈するか」というデコーダは別途必要
- つまり、完全に規則ゼロにはできず、「個別規則列挙」ではなく「役割ベースの生成規則」に落とすのが妥当

結論:

- 「個別の AZIK ルール表を固定する」のではなく、
- 「キー役割の配置 + 役割から出力を決める一般化デコーダ」を最適化対象にする

この整理なら、ユーザーの意図に沿いつつ仕様を明確化できる。

### 2. かな化済みデータを使うという前提

これは現状コードとは一致しない。

`python/dataset.py` では、日本語データを `pykakasi` の `kunrei` でローマ字へ変換し、さらに `clean()` で `qwerty_layout` に含まれる文字だけへ落として `data/ja.txt` を作っている。

つまり現状の `data/ja.txt` は:

- かなではない
- モーラ列でもない
- かな由来のローマ字列である

このため、AZIK 系の評価対象としては現状の加工後データはやや遠い。

結論:

- 「かな化済みデータを使う」という方針自体は妥当
- ただし現実装は「かな化」ではなく「訓令式ローマ字化」なので、前処理の見直しが必要

### 3. 最初に扱う規則を `ん` 系と二重母音に絞る

これは妥当。

理由:

- AZIK 系の効果が出やすい
- 拗音より規則境界が比較的整理しやすい
- 2 打変換としてモデル化しやすい

初期段階では:

- `子音 + 機能キー -> ann / inn / unn / enn / onn`
- `子音 + 機能キー -> ai / uu / ei / ou`

の 2 系統から始めるのがよい。

この分割は妥当である。

- `ん` 系は母音別に 5 パターンへ分けたほうが、後続モーラとの接続を評価しやすい
- 二重母音も `ai / uu / ei / ou` を独立に持ったほうが、頻度差と打鍵価値を反映しやすい
- どちらもキー役割数は増えるが、個別単語規則を直接探索するよりは探索空間を抑えやすい

## 改訂方針

仕様は「固定規則セット方式」ではなく、以下へ改める。

1. 出力対象はかなまたはモーラ列
2. 入力はキーそのものではなく、キーに割り当てられた役割列
3. 役割列を一般化デコーダで出力列へ展開する
4. その展開能力を前提に、物理配置を最適化する
5. 英語評価は現行方式を維持し、日本語評価とは別スコアとして扱う

## 用語

- `出力列`: 入力したいかな列またはモーラ列
- `入力列`: 実際に打鍵するキー列
- `キー役割`: キーに与える機能分類。例: 母音、子音、撥音拡張、二重母音拡張
- `デコーダ`: 入力列とキー役割から、どの出力列へ展開できるかを決める規則系
- `基本打鍵`: 通常のローマ字的な子音 + 母音入力
- `短縮打鍵`: 子音 + 機能キーのような 2 打短縮

## 核となる設計

### 1. 最適化対象を「文字」から「役割付きキー」へ寄せる

現状ではキーへ直接 `a`, `k`, `s` のような文字を置いている。
拡張後は、少なくとも内部表現として次の 2 層を分ける。

- 物理キー位置
- そのキーが持つ役割

役割の例:

- 母音キー
- 子音キー
- 撥音拡張キー
- 二重母音拡張キー
- 句読点や空白などの通常文字キー

ただし完全な抽象役割だけでは足りないため、実際には次のような表現が必要になる。

```rust
enum KeyRole {
    Vowel(VowelId),
    Consonant(ConsonantId),
    SyllabicNExtension,
    DiphthongExtension(DiphthongId),
    Literal(char),
}
```

ここで重要なのは、`ConsonantId` や `VowelId` の物理配置を動かすこと自体が最適化対象になる点である。

### 2. 規則は個別列挙ではなくデコーダで与える

短縮規則を `kz -> kan` のように列挙するのではなく、次のようなテンプレートで表現する。

- `Consonant(C)` + `Vowel(V)` -> `CV`
- `Consonant(C)` + `SyllabicNExtension` -> `C + ん`
- `Consonant(C)` + `DiphthongExtension(X)` -> `C + Diphthong(X)`

この形なら、子音キーの位置が変わっても規則を総書き換えせずに済む。

結局必要なのは「個別規則表」ではなく「役割列から出力列を生成するテンプレート群」である。

### 3. 出力列ベースで評価する

現状の `NGramDB` はローマ字 3-gram 頻度を保存している。
AZIK 系を扱うには、評価対象を「打鍵文字列」から「出力モーラ列」へ切り替える必要がある。

評価の流れ:

1. コーパスから出力モーラ列を得る
2. 各出力列に対し、現在の配置で実現可能な入力列候補をデコーダで生成する
3. その入力列の物理コストを計算する
4. 最小コストまたは期待コストで評価する

## 前処理の見直し

### 現状

`python/dataset.py` の日本語処理は以下になっている。

1. 生テキストを読む
2. `pykakasi` で `kunrei` ローマ字へ変換する
3. `clean()` で英字と一部記号だけ残す
4. `data/ja.txt` に保存する

これは現行の文字配置最適化には使えるが、AZIK 系には不向きである。

### 問題

- `ん` や二重母音を、出力モーラとして直接扱えない
- ローマ字化結果が既に 1 つの入力方式へ寄っている
- 後段で「どの入力方式がよいか」を比較しにくい

### 改善案

日本語データは少なくとも次のどちらかで保持する。

1. かな列
2. かなから分割したモーラ列

推奨は 2。

理由:

- `ん`
- 長音
- 二重母音
- 促音

を個別に扱いやすいからである。

## デコーダ設計

### 最小要件

初期版デコーダは、少なくとも以下を扱う。

- 基本子音 + 母音
- 子音 + `ann / inn / unn / enn / onn` 拡張
- 子音 + `ai / uu / ei / ou` 拡張

たとえば概念上は次のようになる。

```rust
enum Mora {
    Plain { consonant: ConsonantId, vowel: VowelId },
    SyllabicNAfter(ConsonantId),
    DiphthongAfter(ConsonantId, DiphthongId),
}
```

ただし実装では、最終的に既存コーパス頻度と接続しやすい表現を選ぶ必要がある。

### 「自然に規則が決まる」を成立させる条件

ユーザーの意図を成立させるには、次が必要である。

- どのキーが子音か母音かを持つ
- どのキーが `ん` 拡張か二重母音拡張かを持つ
- 役割列が与えられたとき、出力列を一意または少数候補へ展開できる

ここまで入れば、「配置を決めれば規則が自然に決まる」はかなり成立する。
逆にここが無いと、「2 打目の子音が literal な子音なのか拡張記号なのか」が判定できない。

## 評価関数

英語評価:

- ローマ字 tri-gram 頻度
- tri-gram の物理コスト

日本語評価:

- 出力モーラ列頻度
- その出力列を生成する最短または期待入力列
- その入力列の物理コスト

統合評価:

```text
total_score =
  en_weight * english_score(layout)
  + ja_weight * japanese_score(layout, decoder)
```

ここで:

- `english_score` は現行の英語ソース評価をほぼそのまま使う
- `japanese_score` は AZIK 系デコーダを通した出力モーラ列評価を使う

日本語側のスコアは次で与える。

```text
japanese_score =
  Σ freq(output_sequence)
    * best_cost_for(output_sequence, layout, decoder)
```

初期版では日本語側の `best_cost` を使う。

理由:

- 実装が単純
- 規則選択確率を別途設計しなくてよい

ただしこの評価は楽観的なので、後で以下を追加できる余地を残す。

- 認知負荷ペナルティ
- 曖昧性ペナルティ
- 候補分散ペナルティ

## 物理コスト評価

既存の `PhysicalLayout` は 3 打コスト前計算を前提にしている。
AZIK 系では 2 打短縮が重要なので、固定長 3-gram だけでは不十分である。

初期版としては次のどちらかが現実的である。

1. 入力列をスライディング 3 打窓へ分解して近似評価する
2. 2 打コストと 3 打コストの両方を持つ

`ん` 系と二重母音だけを扱うなら 2 打の影響が大きいため、初期版から 2 打コスト導入を優先したほうがよい。
ここは以前の草案より修正が必要な点で、3 打窓の和だけでは短縮入力の差が鈍る可能性が高い。

## 既存コードへの影響

### `python/dataset.py`

- 現状のローマ字化前提では不足する
- 日本語用に、かな列またはモーラ列を保存する出力を追加したい

### `src/n_gram.rs`

- 現行の `LogicalNGram<char>` は英語や単純ローマ字評価には使える
- 日本語 AZIK 系は別構造に切り出したほうがよい
- `MoraNGram` あるいは「出力列頻度テーブル」を新設したい
- 英語用 `NGramDB` と日本語用コーパス表現は分離して持つ

### `src/keyboard_layout/logical_layout.rs`

- `char -> index` のみでは役割最適化を表現しにくい
- `KeyRole` を扱う別レイヤ、または `LogicalLayout` の拡張が必要

### `src/keyboard_layout/physical_layout.rs`

- 2 打コスト API の追加が有力
- 可変長列の評価関数も欲しい

### `src/algorithms/genetic.rs`

- GA 自体は流用できる
- 個体表現を「文字順列」から「役割付きキー配置」へ拡張する必要がある
- 評価器は `english_score` と `japanese_score` を別実装にして、最後に重み付き合成する

## 推奨アーキテクチャ

```text
src/
  input_method/
    mod.rs
    mora.rs
    decoder.rs
    role.rs
  evaluator/
    mod.rs
    english.rs
    japanese.rs
    combined.rs
    sequence_cost.rs
  corpus/
    mod.rs
    ja_mora.rs
```

責務:

- `input_method/mora.rs`
  - モーラ表現
- `input_method/role.rs`
  - 子音、母音、拡張キーなどの役割表現
- `input_method/decoder.rs`
  - 役割列から出力列への展開
- `evaluator/english.rs`
  - 現行の英語 n-gram ベース評価
- `evaluator/japanese.rs`
  - AZIK 系日本語評価
- `evaluator/combined.rs`
  - 英語と日本語の重み付き合成
- `evaluator/sequence_cost.rs`
  - 2 打以上の可変長列コスト評価
- `corpus/ja_mora.rs`
  - 日本語コーパスのかな/モーラ頻度化

## 最初のマイルストーン

1. 日本語コーパスをかなまたはモーラ列で保持できるようにする
2. `ん` 系と二重母音系だけを扱うデコーダを作る
3. キーへ `子音`, `母音`, `拡張` の役割を与える表現を作る
4. 入力候補の 2 打/3 打コストを評価できるようにする
5. 英語評価と日本語評価を別実装に分離する
6. GA の個体表現を役割付き配置へ拡張する
7. 最後に両者を重み付き合成できるようにする

## 未確定点

2. 二重母音拡張は `ai / uu / ei / ou` の 4 役割で開始する

3. 基本入力はどこまでローマ字準拠にするか
   - 訓令式ベースか
   - より抽象的なモーラ分解ベースか

4. 英語最適化との共存をいつ考えるか
   - 評価器は分離し、後で重み付き合成する
